# Discovery tools — Spec

> Feature flow: [/.specs/search.md](../../../../../../.specs/search.md)

## Purpose
Тули пошуку й дослідження музики по 3 джерелах, підключені **прямо до MainAgent** (`DiscoveryTools`, другий
tool-об'єкт у `MainAgentConfig`). Окремого LLM-агента тут більше нема: колишній `DiscoveryAgent` (Haiku, пам'ять
`conversationId + ":d"`) повторював маршрутизацію MainAgent, а його текст викидався, коли були картки. Стратегію
(який тул, скільки пошуків, чи послабити фільтри) тепер обирає MainAgent за правилами свого промпту
([main/spec.md](../main/spec.md)).

**Точковість замість розмитості.** Кожен пошук іде в MusicBrainz + Discogs + Bandcamp **одночасно**, результати
валідуються проти запитаного артиста/назви/треку, і невалідні відкидаються (`AggregatedSearchService` +
`ReleaseMatchValidator`, див. [mainagent/search/spec.md](../../mainagent/search/spec.md)). Один пошук = одна
конкретна річ = один стос карток. Гортати в Telegram десятки випадкових релізів — це не результат.

Пакет також тримає однопризначенні LLM-інтерфейси, які тули викликають у коді: `ReleaseRecommender`,
`MusicResearcher`. Жоден з них не має пам'яті й тулів. Розбір запиту (`SearchRequestExtractor` +
`SearchRequestNormalizer`) живе в `mainagent.search` — ним користуються й прямі пошуки, і `/process`, а пошуковий
домен не має залежати від пакета агентів.

---

## Як тул отримує розмову

Кожен `@Tool` приймає `InvocationParameters parameters` і бере `AgentTurn turn = AgentTurn.of(parameters)`
(див. "AgentTurn" у [main/spec.md](../main/spec.md)). `turn.conversationId()` — основний ID розмови: стан пошуку
(`SearchContextService`, flow_key `search`) пишеться і читається прямо під ним. Суфікса `:d`, `copySearchContext`
і стрипання суфікса в тулах більше нема.

**Межа ходу для стосів.** Тул лише додає стос: `searchContextService.openStack(...)` + `turn.stackOpened(stack)`.
Стоси попередньої відповіді тули не скидають — це робить `MainAgentService` **після** ходу: вдалий хід лишає тільки
свої стоси (`retainStacks`), хід, що впав, прибирає свої (`discardStacks`), див. "AgentTurn" у
[main/spec.md](../main/spec.md). Хід, що нічого не відкрив (промах, треклист, research), стоси не чіпає, тож
⬅️/➡️ на вже надісланих картках працюють далі. `MainAgentService` після ходу шле по повідомленню на кожен
`turn.openedStacks()`.

**Пул пошуків.** `findSimilar` і `exploreAndRecommend` підтверджують кандидатів паралельно на одному спільному
пулі `DiscoveryTools` (`SIMILAR_SEARCH_CONCURRENCY` = 3 потоки на весь бот, закривається на shutdown). MusicBrainz
обслуговує один запит за секунду, тож більше потоків — хоч на виклик, хоч на розмову — лише стояли б у черзі його
rate limiter-а.

**Результат тула** — текст для вступу MainAgent, що будує `StackReport`:
- один стос → `"showed 1 card stack for '<query>' on <sources>: "` + агрегат (`StackReport.describe`);
- кілька стосів → `StackReport.forMainAgent(stacks)` + рядок `Source: <звідки вони>`.

## Модель для web search

| Параметр      | Значення |
|---------------|----------|
| ChatModel bean| `webSearchChatModel` (`AgentModelsConfig`) — **Haiku 5.5** (`agents.web-search.model-name`, дефолт `claude-haiku-5-5`), **окремий** від спільного `haikuChatModel` (LibraryAgent + екстрактори лишаються на `agents.haiku.model-name`), бо тільки цей несе Anthropic server-side `web_search` tool (`web_search_20250305`, `max_uses=3`). Споживачі: `MusicResearcher` і `ReleaseRecommender` (`DiscoveryToolsConfig`), `ListenLinkWebSearch` (`AiExtractorsConfig`, див. [.specs/streaming.md](../../../../../../.specs/streaming.md)) |
| maxTokens     | 8192 (`agents.web-search.max-tokens`; Haiku 5.5 думає за замовчуванням, і thinking рахується в цю стелю) |
| Memory        | немає — кожен виклик самодостатній, контекст розмови розрезолвлює MainAgent перед викликом тула |

Модель викликає `web_search` напряму на інфраструктурі Anthropic — результат приходить у **тій самій** відповіді
API, без client-side виконання. На Sonnet цей server tool свідомо не вішається: його блоки змішувались би з
thinking-блоками в пам'яті й циклі тулів MainAgent.

## Tools (`DiscoveryTools`)

### `search(query)` — точковий пошук
0. **Guard lookup vs explore.** Якщо у витягнутому запиті немає ані артиста, ані назви релізу/треку
   (`MetadataSearchRequest.hasLookupAnchor() == false`) — валідувати результат нема проти чого, тобто це
   насправді explore-запит, який приїхав не в той тул. Такий виклик **автоматично** перекидається в
   `exploreAndRecommend`. Розділення lookup/explore описане в промпті (STEP 0), але промпт — це рекомендація
   моделі, а не гарантія: "пошукай detroit techno класичне" модель стабільно віддає в `search`. Гарантію дає
   саме цей код. Виняток — **лейбл**: це названа річ, і перевірити результат є проти чого, тому такий запит іде
   в `searchLabel` (нижче), а не в explore.
1. `SearchRequestExtractor.extract(query)` → `MetadataSearchRequest` → **`SearchRequestNormalizer.normalize(query, request)`**.
   Екстрактор — це LLM, і два його правила не тримаються на практиці, тому їх доводить до кінця код:
   - **`(BE)` — це не країна.** "Adjust (BE)" — дизамбігуація однойменних артистів у Discogs (і саме так
     юзер копіює назву звідти). Модель стабільно читає дужку як `country=BE`, після чого всі три каталоги
     шукають *бельгійський прес* релізу, у якого його нема, і пошук гарантовано порожній. Правило: якщо
     код країни присутній у запиті саме як `(XX)` — `country` обнуляється. Справжній запит про країну
     формулюється словами ("German techno", "японські релізи"), ніколи дужкою.
   - **"Artist — Title" — це ще й трек.** Без слова album/трек у запиті назва однаково ймовірно і те, і те,
     і промпт просить заповнити обидва поля. Коли модель кладе тільки `release`, весь трековий шлях
     вимикається мовчки: `DiscogsClient.textSearchForTrack` (єдиний, що дістає до треклиста компіляції) і
     deep pass з підтвердженням треклистом обидва загейтовані на `recording`. Правило: `recording` порожній
     + `release` є + у запиті нема album/LP/EP/vinyl/CD/альбом → `recording = release`. Слово "трек"/"track"
     перебиває слово-реліз у тому ж запиті.

   Реальний кейс, на якому це впіймали: "Adjust (BE) - Fractured Elements" — трек з компіляції
   `Various — Air II` (Discogs 33491327). До фіксу пошук ішов як `artist=Adjust, release_title=Fractured
   Elements, country=BE` і давав нуль на всіх трьох каталогах.
2. `AggregatedSearchService.search(request)` — три каталоги паралельно + валідація + (за потреби) підтвердження треклистом.
3. Порожньо → `searchContextService.rememberQuery(...)` (щоб `digDeeper` мав що розширювати) і повернути **перелік застосованих фільтрів** з інструкцією повторити з меншою їх кількістю. Окремо розрізняється `rawCount > 0` ("каталоги віддали N, але жоден не той артист/назва" → швидше проблема написання) від чистого нуля.
4. Знайшло → `searchContextService.openStack(conversationId, query, request, label=null, releases)` — **власний стос** на цей виклик.
5. Return: `"showed 1 card stack for '<query>' on <sources>: <агрегат>"`.

**Викликається кілька разів за хід.** Питає юзер про три речі — три виклики, три стоси, три повідомлення з
картками. Ліміт — 3 на відповідь (більше не читається в Telegram).

### Лейбл у `search` — релізи одного лейблу → до 10 стосів
`MetadataSearchRequest.isLabelLookup()`: є `label`, немає артиста, релізу й треку ("дай пару релізів з Tresor",
"ще щось з того лейблу"). Промпт просить передавати `search("лейбл <назва>")`, а `SearchRequestNormalizer` це
гарантує: якщо запит має рівно таку форму, а модель не заповнила `label`, назва йде в `label`, артист і назви
обнуляються. Голе "Tresor" модель читає як артиста.
1. `AggregatedSearchService.search(request)` → Discogs і MusicBrainz фільтрують за лейблом.
2. `ReleaseMatchValidator` лишає тільки релізи, чий `label` справді збігається із запитаним (без суфіксів типу
   Records/Recordings). Bandcamp лейбла не віддає, тому в такому запиті не бере участі. Каталоги дають кілька
   лейблів на реліз, у Discogs там ще й дистриб'ютори, тому клієнти кладуть у `label` саме запитаний, якщо він є.
   Кап такого пошуку `LABEL_CAP` (60), бо далі лишається один реліз на артиста.
3. Перші `MAX_LABEL_STACKS` (10) релізів від різних артистів → кожен свій стос із label = назва лейблу.
4. Порожньо → той самий шлях, що й у звичайного промаху: `rememberQuery` і перелік фільтрів.

Це перші збіги за релевантністю каталогу, а не найкращі роботи лейблу. Кількість "пару" не враховується: показується все підтверджене до стелі.

### `exploreAndRecommend(topic)` — research → N стосів
Для відкритих запитів ("порадь щось", "що послухати з детройт-техно", "хочу дарк ембієнт 90-х"):
1. `ReleaseRecommender` (окремий `@AiService` на `webSearchChatModel`, тобто **з web search**) отримує тему **і список
   релізів юзера** (`LibrarySearchService.ownedReleases()`, `Artist — Title`, до 400 найновіших) → рівно 10 рядків
   `Artist — Release Title`, у написанні каталогів, найкращі першими. Показується до 3; решта — запас на кандидатів,
   яких нема в каталогах або які вже є в бібліотеці. Список бібліотеки — не лише заборона: з нього модель бачить смак
   і йде далі за хрестоматію. У промпті **нема** прикладу зі справжніми релізами: приклад "classic detroit techno"
   модель копіювала дослівно (журнал прогонів, Ф3) — формат показують вигадані імена.
2. Парсинг рядків детермінований (split по тире), **без** повторного виклику екстрактора — зайві LLM-хопи ні до чого.
   Рядок, що не схожий на пару (назва довша за 100 символів або 12 слів, артист довший за 8 слів), — це проза моделі
   ("Вибачте — не можу надати…"), а не пік, і в каталоги не йде.
3. **Фільтр бібліотеки в коді:** пік, який уже є в бібліотеці (`OwnedReleases.owns` — артист і назва без регістру,
   діакритики, дужок і `[flac]`; "Enter" = "Enter (Deluxe Edition)"), пропускається до пошуку. Промпт — прохання,
   фільтр — гарантія.
4. Решта шукається **хвилями по 5** паралельно (той самий точковий агрегований пошук, `SIMILAR_SEARCH_CONCURRENCY`
   потоків, як у `findSimilar`), наступна хвиля — лише якщо ще нема 3 підтверджених. Десять повних пошуків разом
   тримали б бота під лімітом MusicBrainz удвічі довше, а зазвичай вистачає першої хвилі. Кандидати без
   підтвердження мовчки пропускаються (рекомендація, яку не відкрити, гірша за на один стос менше).
5. Перші 3 підтверджені **в порядку рекомендатора** → `openStack(..., label="Artist — Title", ...)`. Стоси відкриваються вже після всіх пошуків — `openStack` це read-modify-write стану чату.
6. Return: `StackReport.forMainAgent(stacks)` + звідки вони + `Skipped, already in the user's library: …`, якщо
   щось відсіялось, аби MainAgent написав вступ і не радив те, що в юзера є.

Чому одним тулом, а не "research → LLM сам викликає search × 3": цикл всередині тула детермінований і гарантує
форму відповіді (N стосів), а модель при трьох послідовних тул-викликах легко зривається на прозу.

### `findSimilar(seedQuery)` — схоже на X → до 10 стосів
Real similarity, never invented from the LLM's own knowledge. Детермінований кодовий шлях, LLM релізів не вибирає:
1. Seed resolution: if `seedQuery` blank → the release currently in view (same `currentPage` lookup as
   `getTrackList`); artist і title там уже розділені каталогом, тому `MetadataSearchRequest` будується
   напряму, без виклику екстрактора. Інакше — рядок, як його дав юзер (може бути "артист" або
   "артист — назва"), через `SearchRequestExtractor`.
2. `MusicBrainzClient.findArtistMbid(seedArtist)` → MBID, де `seedArtist` = поле `artist` з витягнутого запиту
   (голий seed "symphony of love — spirit of love" як ім'я артиста в MB не резолвиться взагалі).
3. `RelatedArtistsCollector.collect(mbid)` → впорядкований список споріднених артистів, кожен зі своїм MBID і
   причиною. Три джерела (деталі нижче): **прямі** зв'язки сцени, **містки** через спільні групи, **co-listen**.
4. Перші `MAX_SIMILAR_ARTISTS_TRIED` (12) артистів паралельно (`SIMILAR_SEARCH_CONCURRENCY` = 3): для кожного
   `RelatedArtistsCollector.mainRelease(mbid)` дає назву головного релізу → точковий агрегований пошук
   `артист + назва`. Непідтверджені мовчки пропускаються.
5. Перші `MAX_SIMILAR_STACKS` (10) підтверджених у порядку зі списку → `openStack` послідовно (він не
   потокобезпечний) з label `Артист — Назва · причина` і `group` = тип зв'язку. **10 — стеля, а не ціль:**
   менше, значить менше. Перед показом десятка сортується за типом зв'язку (прямі, містки, co-listen): шаблон
   вирішує, хто потрапить у десятку, а на екрані картки йдуть тими ж групами, що й вступ, реальні зв'язки першими.

**Один реліз = один стос, один артист = один реліз.** Пошук тільки за іменем ненадійний: серед псевдонімів
трапляються імена на кшталт `Us` чи `Red Planet`. Пара артист + назва, де назва взята за MBID, цю колізію закриває.
Гортання всередині стосу показує видання цього релізу.

**Чому зв'язки, а не лише co-listen.** Co-listen покриває те, що слухають масово, і тягне до відомих імен. Для
малих сцен кращий сигнал — реальні люди: псевдоніми, групи, спільні проєкти. Це факти з MusicBrainz, а не оцінка.

`RelatedArtistsCollector` (детермінований, без LLM):
- **Люди seed-а:** сам seed, якщо це людина; учасники групи (`member of band`, backward); людина за псевдонімом
  (`is person`, backward). Максимум `MAX_PEOPLE` (4), щоб велика група не з'їла бюджет MusicBrainz.
- **Прямі:** усі люди-учасники, їхні псевдоніми (`is person`, forward) і групи (`member of band`, forward).
  Спершу те, що спільне для кількох людей або є в co-listen, далі по черзі від кожної людини, щоб один учасник
  не зайняв усі місця.
- **Містки:** інші учасники до `MAX_BRIDGE_GROUPS` (4) груп seed-а. Саме так Drexciya доходить до Jeff Mills
  через Underground Resistance.
- **Co-listen:** `ListenBrainzClient.findSimilarArtists(mbid)` за score, MBID береться з відповіді.
- **Порядок:** шаблон пряма, місток, пряма, co-listen по колу; вичерпане джерело пропускається, тому бідне
  джерело добирається іншими. Co-listen має найменше ходів, бо тягне до відомих імен: у Drexciya це Aphex Twin і
  Radiohead. Дублі за MBID викидаються, seed не показується ніколи.
- **Причина:** реальний зв'язок важить більше за co-listen, тому артист, що є в обох, показується зі зв'язком.
  Названо не більше двох джерел, щоб label не розтягував картку.
- **Тип зв'язку:** кожен артист несе `Connection` (`DIRECT`, `BRIDGE`, `CO_LISTEN`), тобто джерело, з якого він
  прийшов. Текст групи з іменем seed-а кладеться в `SearchStack.group` і доходить до вступу (див.
  `StackReport.forMainAgent`). Причина на картці лишається, бо вона пояснює один реліз, а група пояснює логіку вибору.
- **`mainRelease`:** `MusicBrainzClient.browseReleaseGroups(mbid)` (`type=album|ep|single`, без бутлегів).
  Album → EP → Single, без вторинних типів
  (Compilation, Live тощо) раніше за ті, що з ними; при рівності найраніший. Якщо релізів нема, артист пропускається.

Реліз спорідненого артиста, який уже є в бібліотеці, пропускається тим самим `OwnedReleases.owns`, що й у explore,
і потрапляє в рядок `Skipped, already in the user's library: …`. Другий запит "схоже" може показати те саме, що й
перший: стану між запитами нема.

**Style fallback — коли нема кандидатів або жоден не підтвердився.** MusicBrainz+ListenBrainz покривають
те, що люди масово слухають; обскурне вінілове 12" 1993-го (типовий вміст цієї бібліотеки) там не існує —
а в Discogs існує, разом зі стилями. Тому замість тупика:
1. Той самий точковий агрегований пошук по seed → топ-реліз.
2. З нього беруться `tags` (Discogs styles: `acid, techno, trance`) — максимум 3 — і десятиліття з `years` (`1990s`).
3. `exploreAndRecommend("<styles> <decade>")` — юзер отримує стоси, а не відмову.
4. Якщо навіть seed не знайшовся в жодному каталозі (або в нього немає стилів) — тільки тоді відмова
   з проханням уточнити назву.

Це код, а не правило промпту: «знайди схоже» не має права впертись у відсутність рядка в MusicBrainz.

Тригер: "хочу схоже", "порадь щось подібне", "similar to X". Distinct from `manageLibrary`'s library-scoped `findSimilarInLibrary` (audio-feature similarity over the user's own analyzed tracks) — this tool finds NEW music via MusicBrainz relations and ListenBrainz, not what the user already owns.


### `researchMusic(question)` — факти з мережі
Дослідницькі питання без прохання показати релізи ("розкажи про X", "хто такий X", "що за лейбл Y", "дискографія X").
1. `turn.progress("🌐 шукаю в мережі...")`.
2. `MusicResearcher.research(question)` — Haiku з web search, 3-5 речень українською без markdown, тільки факти з
   джерел, опційно голий URL найкращого джерела окремим рядком.
3. Return: відповідь дослідника; MainAgent переказує її, не додаючи фактів з пам'яті.
4. Помилка → `"web research failed — tell the user you could not check this right now"`.

`question` має бути самодостатнім: займенники ("він", "цей лейбл") MainAgent розписує з розмови.
Стосів не відкриває, карток не показує.

### `digDeeper()`
Читає попередній `rawInput` + `MetadataSearchRequest` зі стану пошуку розмови і ганяє
`AggregatedSearchService.searchLoose()` — той самий запит **без валідації**, стос із label "усе підряд".
"Наступний движок по колу" більше не існує: всі три опитуються завжди, тому єдина вісь, по якій ще можна
копнути — суворість.
Тригер: "копай", "ще копай", "покажи все", "dig deeper".

### `getTrackList()`
Бере реліз на екрані: `searchResults` + `currentPage` (`SearchContext.currentPage` в ChatStateStore) під
`turn.conversationId()`. Lazy-fetches повний треклист через `getMetadataWithTracks()`. Повертає пронумерований
список треків, який MainAgent виводить дослівно.
Тригер: "які треки", "tracklist", "що на альбомі" — для релізу, якого **нема** в бібліотеці.

## `StackReport` — текст для вступу

`forMainAgent(stacks)`:
- один стос → агрегат: кількість, джерела, діапазон років, типи, топ-3 лейбли, топ-5 тегів;
- кілька стосів → по рядку на стос (`• <label> — <агрегат>`) + інструкція представити всі;
- більше 3 стосів → ті самі рядки, але інструкція описати спільне між ними, не називаючи кожен (вступ обмежений 600 символами);
- є стоси з `group` (`findSimilar`) → рядки згруповані за типом зв'язку, групи йдуть у порядку показу карток, а
  інструкція просить одним абзацом без markdown пройти групами й сказати, як кожна пов'язана з seed-ом. Ліміт
  вступу тут `MAX_GROUPED_INTRO_CHARS` (900).
  Стоси без групи в тій самій відповіді йдуть окремим блоком.

Для кількох стосів вступ спирається **лише на передані дані**: імена, роки, лейбли й зв'язки поза цими рядками
заборонені, бо модель береться заповнювати прогалини з пам'яті й помиляється. Co-listen названо прямо як збіг
слухачів, а не зв'язок. Правило стосується тільки кількох стосів: у вступі до одного стосу MainAgent і далі
додає власний контекст. Це інструкція моделі, а не гарантія: перевірено на живих даних (Drexciya, Jeff Mills,
по 4 прогони Sonnet), вигаданих людей і зв'язків не було, але епітети сцени на кшталт "детройтське коло" трапляються.

## Hard rules
1. `search()` опитує всі три каталоги одночасно і показує **тільки** підтверджені збіги. Розмитий результат — не результат.
2. Тули не говорять до юзера: вони повертають текст для MainAgent і відкривають стоси; картки шле `MainAgentService`.
3. Якщо нічого не знайшов → повернути застосовані фільтри, щоб MainAgent повторив з меншою кількістю або спитав уточнення.
4. `findSimilar()` ніколи не вигадує схожих артистів з власного знання LLM — тільки зв'язки MusicBrainz,
   ListenBrainz co-listen дані або (fallback) стилі, які реальний каталог написав на самому seed-релізі.
5. `exploreAndRecommend()` показує тільки те, що підтвердилось у каталогах — рекомендація без картки не показується.
   Ні він, ні `findSimilar()` не показують реліз, який уже є в бібліотеці юзера.
6. Група стосу береться з джерела зв'язку в коді, а не з LLM: модель описує групи, але не визначає їх.
7. Жоден запит без анкера (артист/назва/трек/лейбл) не доходить до показу як "пошук" — або explore, або нічого.
8. Тули стоси не скидають — межу ходу закриває `MainAgentService` після ходу (`retainStacks` / `discardStacks`). Інакше
   хід, що впав після першого пошуку, лишив би чат без робочих стосів, а другий пошук ходу міг би затерти перший.
9. Стан пошуку живе під основним `conversationId`; жодних суфіксних ключів.

## SDD checkpoints
- Новий пошуковий движок → `SearchEngine` enum value + `SearchEngineService` impl. Tool-код не змінюється — `AggregatedSearchService` ітерує весь map.
- Змінити суворість збігу → `ReleaseMatchValidator`, не тули.
- Екстрактор систематично плутає поле → правило в `SearchRequestNormalizer` (детерміновано), а не тільки
  абзац у промпті `SearchRequestExtractor`. Промпт — рекомендація, нормалізатор — гарантія.
- Змінити кількість стосів у рекомендації → `MAX_RECOMMENDATIONS`; у `findSimilar` → `MAX_SIMILAR_STACKS`; у лейблі → `MAX_LABEL_STACKS`.
- Новий тип зв'язку або джерело схожості → `RelatedArtistsCollector`, не тули.
- Новий тул → `@Tool` у `DiscoveryTools` + рядок у таблиці Tools у [main/spec.md](../main/spec.md) + правило в `MainAgentPrompts`.
