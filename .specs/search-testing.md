# Search — ручне тестування флоу

Робочий файл для живих прогонів. Юзер пише запит у бот і каже "прогнав такий пошук" та чи результат хороший;
Claude дивиться в логи, як запит ішов, і звіряє з очікуваним шляхом нижче. Каталог описує те, що код робить
**зараз** (станом на `eea44e4`), а не те, що він мав би робити. Розбіжність між очікуваним і побаченим — це і є
знахідка.

Опис самих флоу: [search.md](search.md). Контракти: `mainagent/search/spec.md`, `agents/discovery/spec.md`,
`agents/main/spec.md`.

---

## 1. Як ми це робимо

1. Юзер вибирає кейс із каталогу (або вигадує свій), пише запит у бота, потім мені: "прогнав `<запит>`" + чи
   результат хороший (картки ті, вступ чесний, швидкість).
2. Я читаю логи за цей час (рецепт у §4) і складаю шлях: який тул обрав агент, що передав, скільки знайшли
   каталоги, скільки підтверджено, скільки стосів, час і вартість.
3. Порівнюю з очікуваним шляхом кейсу. Звітую: шлях збігся чи ні, де саме відхилився, чи є помилки в логах.
4. Вердикт юзера (результат добрий чи ні) і мій (шлях правильний чи ні) — **різні речі**, обидва йдуть у журнал
   (§7). Хороший результат на хибному шляху — це удача, яка зламається на іншому запиті.
5. Знахідки не виправляються на ходу: збираються, потім разом вирішуємо, що з них фікс, що — нове правило,
   що — тест.

Не плутати:
- **⛏️ `DIG_DEEPER` (кнопка)** = той самий запит без валідації. Текст **"копай <щось>"** на початку повідомлення
  = прямий пошук у Soulseek для завантаження, зовсім інший флоу (E8).
- **Вердикт каталогів** (`confirmed=`) = що пройшло валідатор, а не що юзер вважає хорошим.

## 2. Карта входів

| Що юзер зробив | Хто обробляє | Скільки стосів |
|---|---|---|
| Вільний текст | `UserInteractionOrchestrator` → `MainAgent` (Sonnet) → тул | залежить від тулу |
| → discovery-тули MainAgent (`DiscoveryTools`) | Sonnet обирає тул сам | |
| &nbsp;&nbsp;`search` — названа річ | екстрактор → нормалізатор → `AggregatedSearchService` | 1 (до 3 за відповідь) |
| &nbsp;&nbsp;`search("лейбл X")` | те саме, `isLabelLookup()` → `searchLabel` | до 10 |
| &nbsp;&nbsp;`search` без анкера | guard перекидає в `exploreAndRecommend` | до 3 |
| &nbsp;&nbsp;`exploreAndRecommend` | `ReleaseRecommender` (web search) → пошук кожного | до 3 |
| &nbsp;&nbsp;`findSimilar` | `RelatedArtistsCollector` (MusicBrainz + ListenBrainz) | до 10 |
| &nbsp;&nbsp;`digDeeper`, `getTrackList` | останній запит без валідації / треки поточного релізу | 1 / 0 |
| &nbsp;&nbsp;`researchMusic` | дослідницьке питання без прохання знайти → `MusicResearcher` (Haiku + web_search) | 0 |
| → `manageLibrary` | `LibraryAgent` (власна бібліотека, не каталоги) | 0 |
| → `downloadMusic(artist, album)` | `MusicDownloadFlowService` → `findForDownload` (той самий валідований пошук) | 0 карток |
| Посилання `http(s)://…` | `showByUrl` → `MetadataUrlFetcher` (без LLM) | 1 |
| Фото | `PhotoSearchFlowService` → vision-екстрактор → `searchDefault` | 1 |
| `/discovery <запит>` | аліас вільного тексту: `MainAgentService.chat(<запит>)` | як тул |
| Кнопки `CARD:`, `DIG_DEEPER`, `DL:`, `STREAM:` | `CallbackDispatcher`, без LLM | |

Шлях пошуку (`search`):
```
запит → екстрактор (Haiku) → SearchRequestNormalizer → AggregatedSearchService
  MusicBrainz ‖ Discogs ‖ Bandcamp (25 с на движок, до 12 на движок)
  → ReleaseMatchValidator: EXACT | TRACK | PARTIAL | NONE
  → deep pass (треклисти компіляцій, бюджет 8), лише якщо сильних < 5 і є recording
  → дедуп (Discogs > Bandcamp > MusicBrainz), cap 20 → openStack
```

звертати увагу, де код найімовірніше помилиться.

## 4. Як читати логи

Додаток: контейнер `smapp`, сервіс compose `sashkomusic`.

```bash
cd /opt/sashko-music/sashko-music
docker compose logs --since 10m sashkomusic 2>&1 | grep -E "tool=|Aggregated search|skipped|falling back|Style fallback|failed|anchor|server-tool|TOTAL|ERROR|Fetching|URL not|Direct download|Auto-selected"
```

Що яка лінія каже:

| Рядок у лозі | Що з нього видно |
|---|---|
| `[agent=main] tool=search args=…` | Який тул обрав MainAgent і з яким запитом (чи розрезолвив займенники) |
| `[agent=web-search] …` | Виклики `MusicResearcher` / `ReleaseRecommender` |
| `Aggregated search: raw=N confirmed=M tracklistsChecked=K artist='' release='' recording=''` | `raw` — що віддали каталоги, `confirmed` — що пройшло валідатор; поля, які витяг екстрактор |
| `search('…') has no artist/title anchor` | Спрацював guard, запит пішов в explore |
| `No confirmed related releases … falling back` / `Style fallback for` | `findSimilar` не знайшов зв'язків, пішов по стилях |
| `Related artist '…' has no release to show` / `had no catalog match` | Чому кандидат не став стосом |
| `Recommendation '…' had no catalog match` / `Release recommender failed` | Explore: що відсіялось, чи впав web search |
| `Engine X failed during aggregated search` | Один каталог недоступний |
| `[agent=…] ↩ tool-result name=… result=…` | Що тул повернув агентові (обрізано) |
| `[agent=…] 💬 text=…` | Текст, який агент згенерував (вступ) |
| `[agent=…] 🌐 server-tool-results=` | Було використано вбудований web search |
| `[flow=…] TOTAL $… (N calls)` | Вартість і кількість LLM-викликів за запит |
| `SearchRequestExtractor failed … falling back to raw query` | Екстрактор впав, пошук пішов по сирому рядку |

Той самий запит у логах зв'язується через `[flow=<id>]` лише в рядках `AgentTraceListener`; решта рядків
(`Aggregated search`, `skipped` тощо) йдуть без id, тому їх прив'язую **за часом і потоком**. Паралельні запити
з двох чатів можуть змішатися: тестуємо по одному.

**Чого в логах нема** (бачу лише побічно):
- повного витягнутого запиту: у `Aggregated search` є тільки `artist`, `release`, `recording`; `label`, `style`,
  `country`, `year`, `format` лише в `tool args` сирого рядка, а не після нормалізатора;
- скільки віддав кожен каталог окремо (тільки сума `raw`);
- який каталог дав обраний реліз після дедупу;
- який саме `Match` (`EXACT`/`TRACK`/`PARTIAL`/`NONE`) отримав кожен кандидат.

Якщо цього бракуватиме для діагностики, це кандидат на невеликий лог (одним рядком на пошук), але лише після
першої пачки прогонів, коли стане видно, чого саме не вистачає.

## 5. Критерії "ок" для будь-якого прогону

Шлях (перевіряю я):
- [ ] обрано правильний тул (див. колонку "Очікуваний шлях");
- [ ] у `args` повний розрезолвлений запит, без займенників;
- [ ] поля екстрактора правдоподібні (артист не злився з назвою, `country` порожній, де не просили);
- [ ] `confirmed > 0` там, де реліз точно існує; `raw > 0, confirmed = 0` відрізняється від `raw = 0`;
- [ ] кількість стосів у межах: `search` 1 (до 3), explore до 3, label до 10, similar до 10;
- [ ] у логах немає `ERROR`, а `WARN` пояснюється (`Engine X failed` допустимий, якщо результат є);
- [ ] час від запиту до першої картки й вартість `TOTAL` у розумних межах (орієнтири фіксуємо після перших прогонів).

Результат (оцінює юзер):
- [ ] картки ті, що очікував; перша — найкраща;
- [ ] вступ чесний: усі імена, лейбли й зв'язки є в даних, ніщо не вигадано;
- [ ] порядок карток збігається з порядком у вступі;
- [ ] відповідь не обіцяє того, чого не показано ("дивись картки", а карток нема).

## 6. Відомі прогалини (не баги прогону, а що вже знаємо)

| Що | Де | Наслідок для тестів |
|---|---|---|
| `findSimilar` для альбому/треку бере лише артиста | `DiscoveryTools.findSimilar` | D4: результат не залежить від альбому |
| Окремої логіки для лейбла й жанру в `findSimilar` нема | там само | D9: непередбачуваний результат; план стратегій у обговоренні |
| Голе ім'я лейбла без слова "лейбл" читається як артист | `SearchRequestExtractor` | B4 |
| Вступ у `findSimilar` інколи містить епітети поза даними ("детройтське коло") | `StackReport.formatGrouped` + промпт | D1, D2: дивитись на кожен факт, не лише на імена |
| `MainAgent` працює з дефолтним effort Sonnet 5.5 | `AgentModelsConfig` (`customParameters` зламані в langchain4j 1.10.0) | Час відповіді та `TOTAL` вищі, ніж планували |

## 7. Журнал прогонів

Один рядок на прогін. "Шлях" заповнюю я з логів, "Результат" — юзер. Дії, які випливають, збираємо внизу.

| Дата | Кейс | Запит (дослівно) | Шлях (мій висновок) | Результат (юзер) | Знахідки |
|---|---|---|---|---|---|
| 2026-11-03 | C + бібліотека | досліди мені детройт техно: глянь спочатку які в мене релізи по цьому, а потім якісь класичні альбоми дай | main → `manageLibrary` + `exploreAndRecommend` паралельно; library-haiku → `searchOwnLibrary("detroit techno")` → 1 реліз (Introversion, жанри `detroit`+`techno`); explore → 3 стеки (Model 500 Classics, Derrick May Innovator, Cybotron Enter); $0.094 | слабко: бібліотека знайшла 1 замість 6 | Ф1 |
| 2026-11-03 | D → C | схоже на Cybotron — Clear; потім «без хіп-хопу»; потім «але для чого ти цей enter даєш, як його я вже маю, deep space також» | findSimilar → немає co-listen → style fallback `electronic electro hip hop 1980s` → Planet Rock / The Message / Rockit; exploreAndRecommend ×2 → 1-й: Enter, Deep Space, Strings of Life (обидва перші вже в бібліотеці); 2-й: з 6 «піків» підтвердився лише Blake Baxter; ~$0.39 за три ходи | погано: дає те, що вже є; лише 1 картка | Ф2, Ф3, Ф4 |

### Знахідки, що чекають рішення

- **Ф1 — `searchOwnLibrary` не бачить мітки.** `search_vector` = назва + артисти + жанри релізу + назви треків.
  Мітки живуть лише в COMM треків (`(detroit techno)`), тому 6 релізів з міткою `detroit techno`
  (Model 500 — Night Drive, Deep Space; Jeff Mills — Lifelike EP; UR — The Final Frontier;
  Underground Resistance — Interstellar Fugitives; CEM3340 & 2030 — Machines Awake EP) не знайшлись.
  Знайшовся натомість Introversion — у нього мітка `raw modern techno`, а `detroit` лише жанровий тег Discogs.
  `websearch_to_tsquery` ще й вимагає обидва слова (AND), а в Interstellar Fugitives жанрів релізу нема взагалі.
  Haiku до того ж назвала жанр `detroit` "міткою детройт-техно".
  **Рішення:** пошук іде ще й по коментах треків (вони клеяться до `search_vector` під час запиту),
  фразові збіги першими, ліміт 10, у результаті окремо `{мітки: …}`. Перевірити повторним прогоном.
- **Ф2 — рекомендації не знають бібліотеки.** Ні `exploreAndRecommend`, ні `findSimilar` не перевіряють, чи
  реліз уже є у юзера: Cybotron — Enter (реліз 177, оброблений того ж вечора) і Model 500 — Deep Space (169)
  прийшли як рекомендації. Юзер: «коли я прошу шось схоже за вайбом … треба враховувати що в мене вже є».
- **Ф3 — приклад у промпті `ReleaseRecommender` — це і є відповідь на detroit techno.** Приклад:
  Model 500 — Classics, Derrick May — Innovator, Juan Atkins — Deep Space, Cybotron — Enter, Inner City — Paradise.
  Перший прогін (Ф1) дав рівно Classics / Innovator / Enter, другий — Enter / Deep Space / Strings of Life / Paradise / Innovator.
  Модель копіює приклад замість дослідження.
- **Ф4 — з 6 «піків» підтвердився один.** Рекомендатор (web search) пише преамбулу й вибачення попри «EXACTLY 5 lines»;
  парсер узяв `Вибачте — не можу надати повну відповідь…` за пару артист — назва і шукав її в усіх каталогах.
  Решта — неточні назви: `Rhythm Is Rhythm — Innovator` (Rhythim Is Rhythim; Innovator — це Derrick May),
  `Kevin Saunderson — Triangle of Love` (трек Kreem, сингл), `Juan Atkins — Techno Music` (трек зі збірки),
  `Eddie Fowlkes — Metroplex Records Releases` (не реліз). Валідатор правильно їх відкинув, але запасних не лишилось.
- **Рішення Ф2–Ф4:** рекомендатор переведено на Haiku 5.5 (`agents.web-search.model-name`); він отримує список
  бібліотеки і дає 10 піків без прикладу зі справжніми релізами; власні релізи код відсіює до пошуку (`OwnedReleases`,
  і в explore, і в `findSimilar`) та повідомляє MainAgent, що пропущено; рядки-проза не йдуть у каталоги; піки
  шукаються хвилями по 5. Перевірити повторними прогонами C і D: чи є серед карток уже наявне, скільки з 10 підтвердилось.
